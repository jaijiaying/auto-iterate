# 轮次协议：证据、决策、最佳版本

五种模式共用。每轮都要检查实际产物或行为，记录预期与实际；评分只在模式细则要求时使用。

## 轮次记录

```markdown
## Round N
- hypothesis: <本轮认为失败的原因或改进机会>
- change: <实际改动、影响文件或产物路径>
- verification: <命令/操作、环境、输入、结果路径；未执行则写原因>

| id | expected | actual | evidence | status |
|---|---|---|---|---|
| E1 | ... | 观察到的行为或产物事实 | 路径、截图、日志或输出 | met / partial / unmet / unverified |

- regression: <此前 met 项是否保持>
- verdict: pass / fail / unverified
- next: <继续时的根因与最小动作>
```

`actual` 写可观察事实，不能只写“已修改”或“基本符合”。`unverified` 表示没有有效验证证据，不能当作通过。硬性项 `unmet` 或 `unverified` 均不得 `pass`。若用户给出验收方法，优先采用；验证成本、环境或权限不允许时记录限制。

## 对照与回归

首轮建立基线；从第二轮起检查所有受改动影响且此前已通过的硬性项。发现回归先修复或回退，再继续新改进。避免每轮盲目运行全部检查；选择足以验证改动和相关回归的测试。

每轮报告最重要的通过项、失败项、验证结果和下一步。未达标且仍有轮次时，直接继续，除非用户要求逐轮确认或下一步需要额外授权。

## 最佳版本与恢复

修改前确保有可恢复的起点；每轮保存产物、差异、版本标识或其他足以恢复的记录。不要覆盖用户已有的未提交改动。`best_so_far` 必须指向**实际可恢复的版本**，不能只记一段变更摘要。

选择顺序：先满足硬性项和护栏，再比较经过验证的清单覆盖与质量/指标；同等结果才考虑较新版本。某轮出现关键回归时，不得因总分较高而选它。若最佳版本不是当前工作区状态，交付前恢复最佳版本并验证恢复结果；无法安全恢复时保留当前状态，明确给出最佳版本位置与恢复步骤，不能声称已交付最佳版本。

## 停滞处理

同一根因连续两轮没有改善时，复查验收假设、输入样本和验证方法，尝试更窄的复现或不同的修复策略。不要重复同一种修改。达到轮次上限即停止，报告最佳版本、剩余差距和后续建议；继续需用户给新的轮次预算。

## Final

记录 `iterate_mode`、`verdict`、`rounds_used`、`delivered`、`best_round`、已执行验证及结果、`unmet/unverified` 清单、必要的恢复或后续步骤。不得把未运行的检查写成通过。
