# 功能迭代

仅用于 `iterate_mode: feature`。主交付是用户能使用的软件功能或交互，允许跨代码、配置、接口、数据和界面修改。以实际行为达标为目标，不以文件已修改或测试数量为目标。

## 形成验收标准

读取用户需求、现有实现、项目说明和相关测试。Brief 记录：

- `feature_name`、`repo_or_app`、`user_outcome`、`done_when`、`constraints`、`max_rounds`（默认 5）。
- `expected_checklist`：每项包含场景、输入/操作、预期结果、验证方式；标记硬性项。至少覆盖核心成功路径、关键失败路径，以及受影响的现有行为。不要凭空增加用户未要求的产品范围。
- `baseline`：当前行为或失败证据。无法运行时明确环境限制，仍可检查静态代码与可运行的局部验证。

把“体验更好”一类抽象目标落实到可观察行为；无法合理推断的产品决策再向用户询问。

## 每轮循环

1. **Plan**：挑选未满足的验收项，分析根因与影响范围。决定最小充分改动和验证方式。
2. **Implement**：修改功能所需文件，遵循项目约定。保留用户已有改动；记录本轮变更和可恢复的版本标识。
3. **Verify**：运行与改动对应的验证，优先真实使用场景或端到端检查，再结合有意义的自动测试、类型检查、构建、日志或静态审查。对 UI 实际操作关键交互；对接口检查响应与副作用。测试需能发现行为错误，不能只镜像实现。
4. **Evaluate**：逐项记录 `expected / actual / status / evidence`。未执行的验证标为 `unverified`，不得写成 `met`。核心场景失败、硬性项未通过或关键回归即 fail。
5. **Diagnose**：将失败连接到具体代码路径、环境或需求缺口。下一轮修根因并复测；已通过场景做针对性回归检查。连续两轮同因失败时调整方法或缩小问题，不重复同一修改。

## 停止与交付

只有硬性验收项通过、必要验证已实际执行且无关键回归时 `pass`。达到轮次上限时停止并复盘；若用户给出新的轮次预算，再继续。若环境/外部依赖阻断、继续尝试需要额外授权或无法取得有效证据，则交付当前最佳状态，列出未通过或未验证场景、证据和下一步。不得把“构建成功”单独当作功能完成。部署、发布、数据迁移等外部动作遵守原任务授权。
